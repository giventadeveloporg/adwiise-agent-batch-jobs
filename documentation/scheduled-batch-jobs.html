Scheduled batch jobs

Five jobs are scheduled inside the running adwiise-agent-batch-jobs process. They are not EventBridge tasks and they are not turned off by an empty Stripe API key. Only subscription renewal writes Spring Batch history rows in batch_job_execution and batch_step_execution.

What keeps them running

BatchJobsApplication.java and BatchConfig.java both enable Spring scheduling. BatchJobScheduler.java registers the five @Scheduled methods. A scheduler thread inside that JVM fires them for as long as the process stays up.

restart: unless-stopped in docker-compose.yml only starts the container again after Docker restarts. It does not run jobs while the container is stopped.

Clock: Spring evaluates cron on the JVM clock. This image does not set TZ, so the hours below are UTC. A container with a different timezone fires at different UTC times even with the same expression.
Two different history tables

PostgreSQL stores the Spring Batch prefix BATCH_ as lowercase. Those framework tables are not the application audit log.

Table Who writes it When a row appears
batch_job_execution and batch_step_execution Spring Batch jobLauncher.run() Only when a Spring Batch job is launched. Today that is subscriptionRenewalJob on the schedule.
batch_job_execution_log BatchJobExecution via BatchJobExecutionService Application audit row. Subscription renewal, Stripe fees and tax, and manual payment summary write here. Email batch and platform billing lock do not.
Do not use started_at. QUICK_START.md queries that column. Spring Batch stores the start in start_time. The job name is on batch_job_instance, not on batch_job_execution.

Why six rows appear from 05:59 to 18:00

On this database the renewal job finds two tenants and launches them in that order: tenant_demo_002, then mosc_malankara_orthodox_2. Each launch inserts one job row and one step row. The first tenant starts a fraction of a second before the hour, so a 06:00 fire is stored as 05:59:59.

Three daytime ticks (06:00, 12:00, 18:00) times two tenants is six rows in both Spring Batch tables. The 00:00 pair is the same job and sits outside that window. On 2026-11-12 the last of those rows finished at 18:00 UTC. The next fire is 00:00 UTC.

Observed on this container: every one of those rows was subscriptionRenewalJob with status COMPLETED. The 02:00 and 02:30 jobs ran in the same process and did not insert those six rows.
Why another machine stays empty

These rows live in the Postgres database named by RDS_ENDPOINT and DB_NAME. This container uses adwiise_agent_db-postgresql-1 and database adwiise_agent_db. Another Docker engine has its own database. The same source writes there only while that machine’s container is running, SUBSCRIPTION_RENEWAL_ENABLED is true, and that database has membership tenants. Sharing the git repo does not share these tables.

Enable flags and cron properties

Subscription renewal

  • SUBSCRIPTION_RENEWAL_ENABLED maps to batch.subscription-renewal.enabled. Default true.
  • SUBSCRIPTION_RENEWAL_CRON maps to batch.subscription-renewal.schedule-cron. Default 0 0 */6 * * *.
  • SUBSCRIPTION_RENEWAL_BATCH_SIZE, SUBSCRIPTION_RENEWAL_MAX_SUBSCRIPTIONS, and SUBSCRIPTION_RENEWAL_DAYS_BEFORE control each launch. Defaults are 100, 10000, and 7.

Daily jobs

  • EMAIL_BATCH_ENABLED and EMAIL_BATCH_CRON. Defaults true and 0 0 2 * * *. Enabled still skips without a template.
  • STRIPE_FEES_TAX_ENABLED and STRIPE_FEES_TAX_CRON. Defaults true and 0 0 2 * * *. This container does not set the enable variable, so the default stays on.
  • MANUAL_PAYMENT_SUMMARY_ENABLED and MANUAL_PAYMENT_SUMMARY_CRON. Defaults true and 0 0 2 * * *.
  • Platform billing lock reads batch.platform-billing-lock.schedule-cron. That key is not in application.yml. The annotation default is 0 30 2 * * *. There is no enable flag.
Stripe being unused does not stop renewal. Clearing STRIPE_DEFAULT_API_KEY leaves SUBSCRIPTION_RENEWAL_ENABLED at its default of true. Set that variable to false and restart the container to stop the six-row pattern.
Query the Spring Batch rows

Run this against the database the container is using. Template and Copy both copy the same statement. There are no parameters to change.

Verify query 
SELECT e.job_execution_id, i.job_name, e.start_time, e.end_time, e.status FROM batch_job_execution e JOIN batch_job_instance i ON i.job_instance_id = e.job_instance_id ORDER BY e.start_time;
Windows single-line SELECT e.job_execution_id, i.job_name, e.start_time, e.end_time, e.status FROM batch_job_execution e JOIN batch_job_instance i ON i.job_instance_id = e.job_instance_id ORDER BY e.start_time;
